## 〇、干净环境定义与准备

**「干净环境」指同时满足以下三条的 Windows 10/11 x64 机器：**

| # | 条件 | 确认方式 |
|---|---|---|
| 1 | **没装 PawnIO** 驱动 | 设备管理器无 PawnIO 相关设备；`sc query PawnIO` 返回「不存在」 |
| 2 | **没装 .NET 10 Runtime** | `dotnet --list-runtimes` 无 `Microsoft.WindowsDesktop.App 10.x`；或该机从未装过 .NET |
| 3 | **无旧配置** | `%APPDATA%\Zentwik`、`%APPDATA%\Zenwik`、`%APPDATA%\ZenForge` 三个目录均不存在 |

**另外两条纪律：**

- **不要用快照回滚后的虚拟机。** 驱动残留会骗人：PawnIO 卸不干净时 SMU 仍可写，验证结论失去意义。每次验证用全新虚拟机或全新用户账户。
- **五步按顺序执行，但每步的判据独立成立。** 某步失败不必中止后续步骤——记录现象后继续，后面的步骤能帮助定位前一步的根因。

**建议同时跑两轮**：一轮用**管理员账户**，一轮用**标准用户账户**。原因见第 3 步的「可能失败模式」。

## 第 1 步：安装

**操作**

1. 确认干净环境三条前提（见第〇节）。
2. 从 `dist/` 取出 `Zentwik-2.0.0-can3-setup-win-x64.exe`，双击运行。
3. UAC 弹窗点「是」。
4. 安装向导一路下一步，勾选创建桌面快捷方式，完成后**不要**立即启动（取消「立即启动 Zentwik」勾选）。
5. 打开 `%ProgramFiles%\Zentwik\`（或安装时选择的 `{autopf}` 路径）查看目录内容。

**预期观察**

- 安装向导窗口正常出现，窗口图标是 Zentwik 自己的图标（不是 Inno Setup 默认的空白/通用图标）。
- 安装过程**不会**出现「缺少 .NET Runtime」相关提示（当前实现如此——`.iss` 没有这项检测；应否提示见「当前已知风险」第 4 条，本步只记录现象）。
- 安装完成后目录内含三个文件：`Zentwik.UI.exe`、`Zentwik.Worker.exe`、`WinIo32.dll`。
- 开始菜单有「Zentwik」与「卸载 Zentwik」两项，桌面有快捷方式。

**判据（全部满足才算通过）**

| # | 判据 |
|---|---|
| 1.1 | `Zentwik-2.0.0-can3-setup-win-x64.exe` 能被 ISCC 成功编译出来（若产物根本不存在，本步直接失败，不进入 1.2） |
| 1.2 | 安装向导图标为 Zentwik 图标，非默认图标 |
| 1.3 | 安装目录同时存在 `Zentwik.UI.exe`、`Zentwik.Worker.exe`、`WinIo32.dll` |
| 1.4 | 开始菜单与桌面快捷方式均存在，指向 `{app}\Zentwik.UI.exe` |
| 1.5 | 记录「缺 .NET 10 时安装过程是否有提示」这一现象（有/无），无论通过与否都要记 |

**可能失败模式**

| 现象 | 含义 |
|---|---|
| 根本没有 setup 产物，CI 或本地 ISCC 报「文件不存在」 | `SetupIconFile` 指向的 `Zentwik.UI/Assets/Zentwik.ico` 不在工作树 |
| 安装成功但目录里没有 exe，只有零散文件或空目录 | `Zentwik.iss:61` 的 `Source: "..\..\dist\portable\*"` 指向的目录没有产物，打出了空壳 |
| 安装向导图标是 Inno 默认图标 | 同上第一条，图标未参与编译 |
| 安装一切正常，双击启动立刻失败且无任何日志 | 缺 .NET 10 Runtime，且安装包没有检测 |

**当前已知风险（截至批次六文档同步前）**

1. **`Zentwik.UI/Assets/Zentwik.ico` 未被 git 跟踪** → CI 干净 checkout 后不存在，ISCC 编译 `SetupIconFile` 失败，**发布链断在此处**。本地开发机因文件已在磁盘而能编译，掩盖问题（典型「本地能过、CI 红」）。
2. **`dist/portable/` 为空**（仅 `.gitkeep`）→ 即使 ISCC 编译通过，`Source` 打包的是空目录，安装出来没有 exe。
3. **`release.yml` 不调用 ISCC** → CI 从不产出安装包，只有便携 zip。
4. **`.iss` 无 .NET 10 Runtime 检测**（`docs/TODO.md` 第 1 条）→ 用户装完双击才崩，且崩在 `StartupCrashReporter` 之前时连日志都没有。

**代码依据**

- `build/installer/Zentwik.iss:22` `#define AppExe "Zentwik.UI.exe"`
- `build/installer/Zentwik.iss:36` `SetupIconFile=..\..\Zentwik.UI\Assets\Zentwik.ico`（相对 `build/installer/`，ISCC 读源码树）
- `build/installer/Zentwik.iss:44` `PrivilegesRequired=admin`
- `build/installer/Zentwik.iss:61` `Source: "..\..\dist\portable\*"; DestDir: "{app}"; Flags: ignoreversion recursesubdirs createallsubdirs`
- `.github/workflows/release.yml:47` / `:51` 两条 `dotnet publish -o ./publish`；`:55` `Compress-Archive -Path ./publish/*`；全文无 ISCC
- `build/zip_portable.py:7` `SRC = "dist/portable"`、`:24` `OUT = "dist/...zip"` —— 该脚本**读**目录、**写** zip，不填充目录

## 第 2 步：首次启动

**操作**

1. 双击桌面快捷方式。
2. 观察 UAC 弹窗次数与出现时机。
3. 观察主窗口状态文本的变化过程。
4. 打开任务管理器，查看「详细信息」页是否有 `Zentwik.UI.exe` 与 `Zentwik.Worker.exe` 两个进程。

**预期观察**

- **UI 自身不弹 UAC**（`asInvoker`），窗口立即出现，标题 `Zentwik`，尺寸约 520×320。
- 状态文本依次变化：`正在启动…` → `正在连接 Worker…` → **弹出一次 UAC**（UI 用 `runas` 拉起提权 Worker）→ 点「是」后变为 `Worker: 已连接`。
- 全程**只弹一次** UAC。
- 任务管理器同时存在 `Zentwik.UI.exe` 与 `Zentwik.Worker.exe`。

**判据**

| # | 判据 |
|---|---|
| 2.1 | UI 窗口出现时**没有**先弹 UAC（UI 自身不要求提权） |
| 2.2 | 状态文本最终为 `Worker: 已连接` |
| 2.3 | 全程 UAC 弹窗次数 = 1 |
| 2.4 | 任务管理器同时存在两个进程 |
| 2.5 | 记录从双击到「已连接」的耗时（干净环境无 PawnIO，可能明显偏长） |

**可能失败模式**

| 现象 | 含义 |
|---|---|
| 点「否」拒绝 UAC，状态停在 `Worker: 未连接` | 预期行为（用户拒绝提权），但需记录 UI 是否给出可理解的提示；UI 最多轮询 90 秒才判定未连接 |
| 状态长时间停在 `正在连接 Worker…` | Worker 启动时在等 PawnIO（`WaitForAvailability(60)` 最长 60 秒），属预期降级；超过 90 秒仍为未连接才是问题 |
| 双击 UI 就弹 UAC | UI 的 manifest 被误改成 `requireAdministrator` |
| 状态为 `未连接` 但任务管理器有 Worker 进程 | 管道连接失败（DACL / 管道名 / 版本号），不是进程没起来 |
| 只有 UI 没有 Worker，且无 UAC 弹窗 | UI 拉起 Worker 的 `Process.Start` 失败（`UseShellExecute` / `Verb` 配置错误） |

**当前已知风险（截至批次六文档同步前）**

1. **Worker 每次启动都会真实写 SMU**（`UFIX` 第 9 条）：`ApplyTuningOnStartup` 默认 `true`，若 `tuning.json` 有已保存值则逐核写 CO + FMax。**干净环境无 PawnIO 时不写**，但会走 `WaitForAvailability(60)`，把管道监听一起推迟最多 60 秒。
2. **UI 侧 `SendAsync` 超时 10 秒 vs Worker 侧 `schtasks` 最坏 30 秒**（`UFIX` 第 14 条）：本步不涉及自启，影响小，但同一套超时常量会在第 3 步生效。
3. 未装 PawnIO 时 SMU 读写全部短路返回、不抛异常（事实卡 §1.5），UI 是否把「SMU 不可用」讲清楚**当前无定义**——本步只记录现象，不判失败。

**代码依据**

- `Zentwik.UI/app.manifest:16` `asInvoker`；`Zentwik.Worker/app.manifest:10` `requireAdministrator`
- `Zentwik.UI/App.xaml.cs:101` 设 `正在连接 Worker…`；`:107` 回传进度；`:109` 终态 `Worker: 已连接` / `Worker: 未连接`
- `Zentwik.UI/WorkerLauncher.cs:92-93` `UseShellExecute = true` + `Verb = "runas"`；`:40` `RetryTotal = 90 秒`
- `Zentwik.Worker/Program.cs:62` 读 `--open-ui`；`:189-194` 拉起 UI 时 `UseShellExecute = false`（已提权，子进程继承令牌，不二次 UAC）
- `Zentwik.Worker/BackendHostService.cs:112` `ApplyFromStore()`；`:133-134` `refresher.Start()` → `watcher.Start()`

## 第 3 步：开机自启

**操作**

1. 在 UI 主窗口勾选「开机自启」，等待状态稳定（复选框恢复可点）。
2. 打开「任务计划程序」，找到 `ZentwikAutoStart`，查看「触发器」与「操作」两个页签。
3. 注销当前用户或重启，重新登录。
4. 登录后**不做任何操作**，计时并观察进程与窗口。
5. 回到 UI 取消勾选「开机自启」，再到任务计划程序确认任务消失。

**预期观察**

- 勾选后复选框保持勾选态，无错误弹窗。
- 任务计划程序中存在 `ZentwikAutoStart`：
  - 触发器：**登录时**，延迟 **15 秒**；
  - 操作：`Zentwik.Worker.exe`，参数 `--open-ui`；
  - 常规页：「使用最高权限运行」被勾选。
- 登录后约 15 秒，`Zentwik.Worker.exe` 出现；因带 `--open-ui`，`Zentwik.UI.exe` 与主窗口随后出现。
- 取消勾选后，任务计划程序中 `ZentwikAutoStart` 消失。

**判据**

| # | 判据 |
|---|---|
| 3.1 | 勾选后无错误弹窗，复选框稳定在勾选态 |
| 3.2 | `ZentwikAutoStart` 存在，触发器为登录时 + 延迟 15 秒 |
| 3.3 | 任务操作的参数含 `--open-ui`，RunLevel 为最高权限 |
| 3.4 | 登录后 15 秒左右 Worker 进程出现，且 UI 窗口随之出现 |
| 3.5 | 取消勾选后任务消失（`Get-ScheduledTask` 查不到 `ZentwikAutoStart`） |

**可能失败模式**

| 现象 | 含义 |
|---|---|
| 勾选后弹「设置失败」，复选框回滚，但任务计划里任务已存在 | `UFIX` 第 14 条：UI 10 秒超时先到，Worker 侧实际已创建 |
| 复选框回滚、任务已建，且弹「任务计划已注册但配置保存失败」 | `UFIX` 第 13 条：IPC 成功但 `ui.json` 保存失败，三处状态不一致 |
| `schtasks /Create` 静默失败，UI 报失败 | 组策略限制了任务计划创建权限 |
| 任务存在但登录后 Worker 没起来 | 当前用户不是管理员组成员，`HighestAvailable` 只拿到标准用户令牌，或任务被策略禁用 |
| Worker 起来了但 SMU 全不可用 | 标准用户令牌 + 无 PawnIO，双重降级（记录现象即可） |
| 登录后起了两个 Worker | `Global\Zentwik.Worker.SingleInstance` 互斥体未生效，或旧任务未删 |

**当前已知风险（截至批次六文档同步前）**

1. **`UFIX` 第 13 条未修**：`Save()` 抛异常时只回滚内存与复选框，**不撤销已注册的任务**。方向是「用户以为关了、实际开机还会起来」，界面上完全看不出异常。
2. **`UFIX` 第 14 条未修**：UI 侧超时固定 10 秒，`AutoStartService.Enable()` 最坏 30 秒（`/Create` 15 秒 + 回查 15 秒）。
3. **组策略收紧的机器上 `schtasks` 可能静默失败**（交接文档坑 5），需分别用管理员账户与标准用户账户各跑一轮。
4. **「UAC 被禁用」本身不会让管理员账户降级**：真正失败的是「当前用户不是管理员组成员」与「组策略限制任务计划」。

**代码依据**

- `Zentwik.Core/Services/AutoStartService.cs:49` `TaskName = "ZentwikAutoStart"`；`:52` `DelaySeconds = 15`
- 同上 `:149` `/Create /TN ... /XML ... /F`；`:249` `Delay = PT15S`；`:257-258` `InteractiveToken` + `HighestAvailable`；`:285` `Arguments`
- `Zentwik.Worker/PipeServerService.cs:229` / `:232` 处理 `register-autostart` / `unregister-autostart`
- `Zentwik.UI/MainWindow.xaml.cs:97` `TimeSpan.FromSeconds(10)`（IPC 超时）

## 第 4 步：关闭行为

**操作**

分三个独立子场景，每个场景前先让 UI 与 Worker 都处于运行状态。

1. **默认模式点 X**：点主窗口右上角关闭按钮，观察进程。
2. **托盘模式点 X**：切到托盘模式（或按当前实现的托盘入口），点 X，观察窗口、托盘图标与进程；再双击托盘图标看能否恢复。
3. **托盘右键「退出」**：右键托盘图标选「退出」，观察是否有确认对话框、UI 与 Worker 是否都退出。

**预期观察**

- 场景 1：UI 进程退出，Worker 进程也随之退出（默认 `CloseBehavior.Exit`）。
- 场景 2：窗口消失，托盘图标仍在，任务管理器中 `Zentwik.UI.exe` 仍在（窗口已销毁而非隐藏）；双击托盘图标能重新打开窗口。
- 场景 3：**当前实现无确认对话框**，点「退出」立即执行；UI 与 Worker 都退出。

**判据**

| # | 判据 |
|---|---|
| 4.1 | 场景 1 结束后任务管理器无 `Zentwik.UI.exe` 与 `Zentwik.Worker.exe` |
| 4.2 | 场景 2 结束后 `Zentwik.UI.exe` 仍在，托盘图标仍在，窗口不可见 |
| 4.3 | 场景 2 双击托盘图标能重新打开窗口（不是崩溃或静默无反应） |
| 4.4 | 场景 3 记录「是否有确认对话框」这一现象（当前预期：无） |
| 4.5 | 场景 3 结束后两个进程均退出，无残留 Worker |

**可能失败模式**

| 现象 | 含义 |
|---|---|
| 场景 2 点 X 后整个应用退出、托盘图标消失 | `ShutdownMode` 不是 `OnExplicitShutdown`，销毁主窗口直接结束应用 |
| 场景 2 双击托盘图标抛异常或无反应 | 窗口是 `Hide()` 而非销毁，或 `MainWindow` 引用未置空 |
| 场景 3 后 Worker 仍常驻 | `ShutdownIfOwned` 的 fire-and-forget 任务未完成，进程已退出 |
| 场景 1 后 Worker 仍常驻 | 同上；或 `_startedByUs` 判定为 false（Worker 非本次 UI 拉起） |
| 场景 3 弹出了确认框 | 说明 §7.4 第 4 条已实现，与当前记录不符，需更新事实卡 |

**当前已知风险（截至批次六文档同步前）**

1. **`ShutdownIfOwned` 竞态未修**：`WorkerLauncher.cs:163` 是 `public static void`、`:171` 是 `_ = Task.Run(...)`，`App.xaml.cs:153` 同步调用且无 `.Wait()`，紧接着 `:158-159` `Log.Flush()` / `Log.Dispose()` 就进入进程退出。shutdown 命令可能根本没发出去，失败现场也可能因日志已 Dispose 而丢失。
2. **§7.4 第 4 条部分实现**：菜单项分离已落地（「打开」/「退出」），但**退出无确认对话框**（`TrayIcon.cs:35-36` 直接 `Application.Current.Shutdown()`）。
3. 场景 2 依赖托盘入口，而「托盘模式」当前由 `CloseBehavior` 静态属性决定，UI 壳子**尚未提供切换入口**——本步可能需要临时改代码或直接调 `CurrentCloseBehavior` 才能覆盖三个场景。这一点本身就是待补的功能缺口。

**代码依据**

- `Zentwik.UI/App.xaml:4` `ShutdownMode="OnExplicitShutdown"`
- `Zentwik.UI/MainWindow.xaml.cs:184-195` `OnClosed` 按 `CurrentCloseBehavior` 分支：`Exit` / `WorkerOnly` → `Shutdown()`；`Tray` → 仅把 `MainWindow` 置 null
- `Zentwik.UI/TrayIcon.cs:35-36` `退出` 菜单项 → `Application.Current.Shutdown()`，无 `MessageBox`
- `Zentwik.UI/App.xaml.cs:153` `ShutdownIfOwned()`；`:158-159` `Log.Flush()` / `Log.Dispose()`
- `Zentwik.UI/WorkerLauncher.cs:163` / `:171` `public static void` + `_ = Task.Run(...)`

## 第 5 步：日志位置

**操作**

1. 完成第 2～4 步后，打开 `%APPDATA%\Zentwik\`。
2. 进入 `Logs\` 子目录，列出全部文件。
3. 打开当天的 `zentwik-YYYYMMDD.log` 与 `worker-YYYYMMDD.log`，确认两者都有内容。
4. 检查 `Logs\` 下是否存在超过 14 天的日志文件。

**预期观察**

- `%APPDATA%\Zentwik\` 下存在 `Logs\` 目录，以及 `ui.json`、`tuning.json` 等配置文件。
- `Logs\` 下**同时**存在 `zentwik-YYYYMMDD.log`（UI）与 `worker-YYYYMMDD.log`（Worker），日期为当天。
- 两个文件都非空；`worker-` 文件含启动、管道监听相关记录。
- 不存在修改时间早于 14 天前的 `.log` 文件。

**判据**

| # | 判据 |
|---|---|
| 5.1 | `%APPDATA%\Zentwik\Logs\` 存在 |
| 5.2 | 同一天内**两个前缀**的日志文件都存在（缺任一个即失败） |
| 5.3 | 两个文件均非空，且 `worker-` 文件含启动记录 |
| 5.4 | 无超过 14 天的日志残留 |
| 5.5 | `%TEMP%` 下**没有** `zentwik-*.log` 或 `worker-*.log`（有则说明落错目录） |

**可能失败模式**

| 现象 | 含义 |
|---|---|
| 只有 `worker-*.log`，没有 `zentwik-*.log` | UI 侧 `LogService` 未设 `Directory`，日志落到 `%TEMP%` |
| `%TEMP%` 下出现 `zentwik-*.log` | 同上（`UFIX` 第 12 条的坑） |
| `Logs\` 目录根本不存在 | `AppPaths` 迁移或创建失败；或进程没有走到写日志的路径 |
| 日志文件存在但为空 | 日志缓冲未 Flush（进程被强杀，或 `Log.Dispose()` 被竞态跳过） |
| 有 14 天前的日志 | 保留策略未生效 |

**当前已知风险（截至批次六文档同步前）**

1. **`UFIX` 第 12 条**：`LogOptions.Normalize()` 在 `Directory` 为空时回落到 `Path.GetTempPath()`。走 DI（`AddZentwikCore`）的宿主会自动填 `AppPaths().Logs`；**手工 `new LogService` 的宿主必须显式设 `Directory`**，否则静默落 `%TEMP%`。UI 已按规范显式设置，但这条坑只在「忘写」时暴露，且表现是静默的。
2. 日志保留 14 天，由 `LogService` 启动时清理；若 UI 与 Worker 同时清理同一目录，需观察是否互相删错（本步只记录，不判失败）。
3. `UFIX` 第 11 条提醒：诊断客户端曾放在 `%TEMP%\zwclient\`，**不要**假设该路径存在，也不要把它当作日志目录。
