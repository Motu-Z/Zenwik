## 2. 编译红线

**编译红线：0 警告 0 错误。** 任何引入警告的写法都要消掉再提交。

### 2.1 提权进程的调试约束（批次三收尾补入）

**`Zentwik.Worker` 是 `requireAdministrator` 进程，非提权 shell 的 `Stop-Process` / `taskkill` 杀不掉它**（返回 `拒绝访问`）。

调试时需用**提权 shell**，或从提权上下文执行 `taskkill /F /PID`。批次三做管道 DACL 矩阵实验时因此**作废过一轮**——5 个模式全连到同一个旧实例，因为旧的提权 Worker 没被杀掉，而脚本把 `拒绝访问` 当成了「管道未就绪」，于是每个模式测的都是同一份旧代码。

操作习惯：改完 Worker 后**先确认旧进程已消失**（`Get-Process Zentwik.Worker` 为空）再启动新的；否则测的是旧代码。若没有提权 shell，可通过管道发 `shutdown` 让 Worker 自己退出——前提是管道还能连上。

### 2.2 单实例互斥体的日志实现（批次三收尾补入）

`Zentwik.Worker/Program.cs` 的 `!createdNew` 分支（单实例互斥体被占用时）写 `%AppData%\Zentwik\startup_crash.log`，记录「Worker 已在运行，单实例互斥体被占用，本次启动退出」。

**实现要点三条**：

1. 先 `Directory.CreateDirectory(Path.GetDirectoryName(logPath))`——首次运行时 `%AppData%\Zentwik\` 目录可能不存在，`File.AppendAllText` 会抛 `DirectoryNotFoundException`
2. 整个分支包在 `try/catch` 里——日志写失败静默 `return 0`，不能抛异常。原因：该分支在 `AppDomain.UnhandledException` 注册**之前**执行，异常处理器还没挂上，抛出去会让第二个实例**崩溃**而不是静默退出
3. `mutex.Dispose()` 在 `try/catch` 之外（或之内均可，只要不抛），不能因为日志写失败而泄漏互斥体句柄

这个分支的失败模式是「第二个实例崩溃而不是静默退出」，与单实例设计的核心承诺相反。批次三实测 4 次重复启动，`startup_crash.log` 出现 4 条记录，进程静默退出——实现正确。

### 2.3 fire-and-forget 的日志在进程退出时会丢（批次四补入）

`ShutdownIfOwned` 这类 fire-and-forget 的日志在 UI 进程退出时可能丢失——Exit 模式下 UI 日志没有「已请求 Worker 退出」行，是因为 fire-and-forget 任务在进程退出后完成，日志被 `Dispose` 丢弃。

排障时不要以「UI 日志没有 shutdown 记录」为依据判断 Worker 没收到 shutdown，看 Worker 日志的退出记录。

> 批次四实测：Exit 模式三次运行，UI 日志均止于「Worker 已就绪」，无 shutdown 行；同期 `worker-*.log` 在 UI 退出后仍有落盘写入（`StopAsync` 里的 `log.Flush()`），Worker 确实优雅退出。两侧日志必须合起来读，单看 UI 侧会得出相反的结论。

fire-and-forget 日志丢失有两个原因：一是进程退出时 `Task.Run` 还没执行完；二是 `OnExit` 里先 `ShutdownIfOwned()` 后紧接着 `Log.Dispose()`，如果 fire-and-forget 任务在 `Log.Dispose()` 之后才执行到 `App.Log.Info`，会撞上已 Dispose 的 `LogService`，抛 `ObjectDisposedException`。注意 catch 块自身也会失效——`catch (Exception ex)` 里调 `App.Log.Warn` 同样撞已 Dispose 的 `LogService`，再抛一次 `ObjectDisposedException`，这次不在 try 覆盖范围内，成为未观察的 Task 异常。.NET 默认不因未观察 Task 异常崩应用（除非配置了 `ThrowUnobservedTaskExceptions`），所以实际不会崩，但意味着失败原因也没有被记录。排障时如果看到 UI 日志缺失 shutdown 记录且没有「ShutdownIfOwned 失败」警告，两个原因都要考虑：进程退出太快，或 `Log` 已 Dispose 导致 catch 块也失效。

另外，`App.OnExit` 的 catch 块用 `System.Diagnostics.Debug.WriteLine` 而不是 `App.Log.Error`——这是正确的防御：`OnExit` 的 catch 可能捕获的正是 `Log.Dispose()` 抛出的异常，此时 `Log` 已不可用，写 `App.Log` 会二次抛。不要「修复」成 `App.Log.Error`。

### 2.4 `ShutdownIfOwned` 的 fire-and-forget 竞态（批次四补入，未修）

此外，`ShutdownIfOwned` 的 fire-and-forget 还存在一个竞态风险：如果 UI 进程在 `Task.Run` 任务完成之前退出，shutdown 命令可能没有被发送，Worker 不会被关闭。批次四实测中 Worker 确实优雅退出了，但这不保证每次都会工作。

批次五的改进方向：将 `ShutdownIfOwned` 改为返回 `Task`（如 `ShutdownIfOwnedAsync`），然后：

- **方向 A**：在 `OnExit` 中 `ShutdownIfOwnedAsync().Wait(TimeSpan.FromSeconds(2))`。`.Wait()` 会阻塞 UI 线程退出最多 2 秒——这是可接受的权衡；如果 UI 线程上还有其他阻塞操作，届时考虑方向 B。
- **方向 B**：改为在 `OnClosed` 中先 `await ShutdownIfOwnedAsync()` 再 `Application.Current.Shutdown()`。需要将 `OnClosed` 改为 `async void`——WPF 的 `Closed` 事件支持 `async void` 处理器，但默认签名是 `void`，不改签名直接写 `await` 会 CS4033。

方向 B 需同步移除 `OnExit` 中现有的 `ShutdownIfOwned` 调用，避免重复发送。**两个方向选其一，不要同时做。** 当前轮不修改，只记录风险。

**截至批次五收尾，竞态仍存在，未修**：`WorkerLauncher.cs:163` 仍是 `public static void`、`:171` 仍是 `_ = Task.Run(...)`，`App.xaml.cs:153` 同步调用且无 `.Wait()`。

### 2.5 不要「修复」`WFO0003`（批次四补入）

`Zentwik.UI.csproj` 的 `NoWarn` 包含 `WFO0003`，原因是 WinForms 分析器要求把 DPI 设置移出清单，但 WPF 的 DPI 感知只能来自清单，移除会让主窗口发虚。不要「修复」这条警告。

> 该工程 `UseWPF` 与 `UseWindowsForms` 同时为 true（托盘需要 WinForms `NotifyIcon`，事实卡 §7.2），但入口点是 WPF 的 `App.xaml` 生成的 `Main`，从不调用 `ApplicationConfiguration.Initialize()` / `SetHighDpiMode`，因此分析器建议的替代机制在本工程根本不存在执行点。抑制理由写在 csproj 里，改代码前先读那段注释。

### 2.6 IHost 接口没有 Lifetime 属性（批次五补入）

`IHost` 接口没有 `Lifetime` 属性（`Host` 类有，`IHost` 接口没有）。要访问 `ApplicationStarted` / `ApplicationStopping` 回调，用 `host.Services.GetRequiredService<IHostApplicationLifetime>()`。写成 `host.Lifetime.ApplicationStarted.Register(...)` 会 CS1061 编译错误。

## 4. 架构红线：UI 层禁止自行 new Core 服务

（原 §2「页面装配」行中与 UI 框架无关的部分，逐字搬运）

> 构造参数全部来自 Core 服务注入，UI 层禁止自行 `new`。

这条在双进程下比单进程时更硬：UI 进程非提权，Core 里大量操作（SMU 写入、注册表、任务计划）在 UI 侧根本没有权限做，
`new` 出来的实例只会静默失败或抛权限异常。所有需要权限的调用一律走 IPC 交给 Worker。
