## 一、全局红线（跨批次）

### 1.1 CHANGELOG 的修复声明不可全信

**规则**：涉及行为的判断以代码和测试为准，CHANGELOG 仅作线索。

**理由**：CHANGELOG 记录的是「声称做了什么」，不是「实际做了什么」。A-3 已核实两处偏差——1.0.4 声称 `MaxEntries = 320`，实际 `LogOptions.cs:26` 是 200；2.0.0-can2 声称「26 项检查全绿」，实际是 24 项唯一检查 + 2 对互斥分支（`smu.construct` / `cpuset.topology` 各是 try/catch 双分支，运行时只会走其中一条）。照抄 CHANGELOG 写文档或写测试，会把不准确的数字固化进契约。

### 1.2 创建 PipeRequest / PipeResponse 时必须显式赋值 Version

**规则**：任何 `new PipeRequest { ... }` / `new PipeResponse { ... }` 都要带 `Version = WorkerPipeContract.ProtocolVersion`。

**理由**：`Version` 是无初始化器的 `int`，默认值 0（`PipeRequest.cs:28`、`PipeResponse.cs:23`），会被 `ValidateVersion` 拒绝。而对端只会返回「UI 与 Worker 版本不一致，请重新安装」这条误导性消息——排查时会先怀疑安装包版本、重装一遍，最后才想到是构造代码少写了一行。这个失败模式无法从日志归因：日志里看到的是版本号不符，不是「谁忘了赋值」。

### 1.3 所有 JSON 序列化必须带 JsonTypeInfo 或 JsonSerializerContext 重载

**规则**：Core 内所有 `JsonSerializer.Serialize` / `Deserialize` 调用都显式传入 `JsonTypeInfo<T>` 或 `JsonSerializerContext` 派生实例；无参单参数重载与泛型反射重载零命中。

**理由**：Core 开了 `IsAotCompatible=true`，无参反射重载会触发 IL2026 / IL3050，在 Native AOT 发布时直接失效或体积失控。现有代码全部合规（A-1 逐条核对过），新代码也必须合规——这不是风格偏好，是构建期就会被裁掉的能力。

### 1.4 Worker 绝不读 UiSettings.BackendService

**规则**：Worker 侧代码不得读取该字段；UI 可读但仅作展示，不得作为启动 / 停止 Worker 的依据。

**理由**：这个字段在旧单进程架构下是「是否允许后台服务运行」的总闸，默认 `false`。双进程下常驻与否由「谁拉起它」决定，不由这个字段决定。Worker 读它会导致启动即退出（默认 false 直接判死）；UI 拿它当开关会与「开机自启」这个选项重复，两个开关管同一件事，用户永远说不清哪个生效。

### 1.5 Worker 绝不调 ProcessWatcher.SetHostVisible(false)

**规则**：Worker 内不得出现该调用。

**理由**：`SetHostVisible(false)` 会挂起 WMI 降级轮询，WMI 不可用时就彻底失去进程监听（连降级路径都没了）。Worker 自己没有「窗口最小化」这种场景需要它，调它只有害处。

### 1.6 Worker 不主动调 ProcessRefresher.SetHostVisible

**规则**：Worker 侧不得主动设置该开关。

**理由**：Worker 无人 `AcquireWatch()`，`IsWatched=false` 时天然不采样——闸门已经在那儿了。主动设 false 会与 `IsWatched` 闸门叠加，同一个行为被两处状态机控制，出问题时无法判断是哪个闸门挂的（A-3 已确认「Worker 永不采样」的说法不成立：真正卡住的是同一条 if 里的 `IsWatched`，且 `RequestSample` 仍能唤醒采单帧）。**UI 侧是否需要控制 `ProcessRefresher` 的采样、如果需要该走什么通道，当前未定义，不在批次三范围内。**

## 二、批次三（Worker）专属红线

### 2.1 OutputType 必须是 WinExe

**规则**：`Zentwik.Worker.csproj` 的 `OutputType` 写 `WinExe`。

**理由**：双击不能弹黑色 Console 窗口。写成 `Exe` 后编译、运行、日志全都正常，只有用户双击时才会看到黑框——验收清单里如果没有「双击看有没有控制台」，这个错误会一路带到发版。

### 2.2 BackendHostService.StartAsync 里 SMU 探测的 catch 块只 Warn

**规则**：catch 块只 `log.Warn(...)`，绝不 `throw`，绝不 `Environment.Exit`。

**理由**：没装 PawnIO 的机器上，进程监听、场景切换、绑核这些功能还要继续可用。SMU 不可用是「部分功能降级」，不是「整个 Worker 无意义」——抛出去会让一个可选硬件依赖变成启动硬门槛。

### 2.3 shutdown 命令必须用 IHostApplicationLifetime.StopApplication()

**规则**：处理 `shutdown` 时调 `StopApplication()`，绝不用 `Environment.Exit`。

**理由**：`StopApplication()` 会触发 `StopAsync`，让 `BackendHostService` 走完 `watcher.Stop()` 和 `log.Flush()`；`Environment.Exit` 会跳过这些清理，导致日志最后一段丢失（恰好是最需要看的那段崩溃现场）、WMI 订阅没释放。

### 2.4 NamedPipeServerStream 必须用显式 DACL 限定到当前用户 SID

**规则**（批次三修正后）：用 `NamedPipeServerStreamAcl.Create(...)` 创建管道，传入 `PipeSecurity`，DACL 只授予当前用户 SID（`WindowsIdentity.GetCurrent().User`）的 `PipeAccessRights.ReadWrite`。**不得放宽到 `BuiltinUsers` 组**——后者是「所有本地用户组」，多用户机器上允许其他登录用户连 Worker 发 `shutdown`。

**理由**：限制只有同用户 SID 的进程能连接管道，防止其他 Windows 用户会话的进程连进来伪造请求。Worker 是提权进程，如果不限制，任何用户都能向它发 `shutdown`——这是一条本地提权 / 拒绝服务的入口。

**【批次三后已修正】** 原规则为「创建管道时显式传 `PipeOptions.CurrentUserOnly`」，该规则在批次三实测中被推翻：提权 Worker + 非提权 UI（中完整性）场景下，`CurrentUserOnly` 管道对中完整性客户端返回 `UnauthorizedAccessException`，UI 连不上 Worker。改用 `NamedPipeServerStreamAcl.Create` + 显式 `PipeSecurity`（当前用户 SID + `ReadWrite`）后，非提权客户端能正常连接。两种机制意图相同（仅当前用户可连），但 `CurrentUserOnly` 在跨完整性级别场景下不足。

原规则（已失效）：创建管道时显式传 `PipeOptions.CurrentUserOnly`。

**附带技术事实**：
- `System.IO.Pipes.AccessControl` 在 .NET 10 是共享框架内建程序集，不需要额外 NuGet 包
- `SetAccessControl` 在已创建的管道上调用会让 accept 循环 fault，必须用 `NamedPipeServerStreamAcl.Create`
- `NamedPipeServerStreamAcl.Create` 的参数名是 `inheritability`，不是 `handleInheritability`

## 三、十二组合矩阵的实现约束

**核对结论（2026-11-01，A-4 闭环后）**：`docs/项目事实卡.md` §7.4「收托盘」的实现约束（:469–:475）**已包含下列全部四条，无缺失，本次未改动事实卡**。

实现 UI 时逐条对照（完整版在事实卡 §7.4，此处为快速对照）：

| # | 约束 | 一句话理由 |
|---|---|---|
| 1 | 收托盘时**销毁 `MainWindow`**，不是 `Hide()` | `Hide()` 保留整棵可视树与设备资源，内存停在 50-70MB；销毁窗口只留 `Application` + `NotifyIcon`，预期 30-40MB。这是「收托盘」相对「最小化」的唯一实际收益。 |
| 2 | `ShutdownMode` 必须是 `OnExplicitShutdown` | 默认的 `OnMainWindowClose` 会在销毁主窗口时直接结束整个应用，收托盘变成退出，托盘图标一闪即消失。 |
| 3 | 关闭前保存 `ui.json`，下次打开从配置读回恢复状态 | 窗口已销毁，内存状态不存在了；不落盘就没有「下次打开位置和上次一样」这件事，只能靠猜。 |
| 4 | 托盘右键菜单的「退出」是**彻底退出**（等价 B1），不等同于关闭窗口（B2） | 两者语义不同（B1 连 Worker 一起停，B2 只收窗口）。菜单里混成一个「退出」，用户点了一次以为只是关窗口，结果后台服务也停了；反过来想彻底退出的人会发现 Worker 还在跑。必须给不同菜单项 + 不同确认文案。 |

**另一条不在这四条里但同样写死的**：托盘图标在 **UI 进程**用 WinForms `NotifyIcon` 创建，Worker 不持有任何托盘（UIPI：高完整性进程的窗口收不到低完整性进程的输入消息，托盘菜单点击会失效）。见事实卡 §7.2。

## 四、批次五收尾 / 批次六文档同步（2026-11-02）

### 4.1 新增资源文件必须确认被 git 跟踪

**规则**：任何新增的构建输入资源（图标、清单、脚本、模板等）在交付前必须确认**已被 git 跟踪**。本地文件存在不等于仓库有文件，CI 以干净 checkout 为准。Agent 若因红线不能执行 git，必须在交付物中明确标注「该文件未被跟踪，需人工 `git add`」。

**理由**：批次五从 `Legacy/WPF/Zentwik/Assets/Zentwik.ico` 复制 `Zentwik.UI/Assets/Zentwik.ico`（32571 字节）到新工程，本地编译与本地 ISCC 全部正常；但该文件未被 `git add`，CI 干净 checkout 后不存在，`Zentwik.iss:36` 的 `SetupIconFile` 指向空路径，ISCC 编译直接失败。这是典型「本地能过、CI 红」，且失败信息指向图标路径，不指向「忘记提交」。已核实 `.gitignore` 第 34–40 行仅忽略图片格式且 `!Assets/**` 放行 `Assets/` 下一切，**无 `*.ico` 排除规则**——原因就是没提交，不是被忽略。详见 `docs/UFIX.md` 第 15 条、事实卡 §1.3。

### 4.2 `--open-ui` 命令行参数与 `CommandOpenUi` 管道命令不可混用

**规则**：两者名称相近但不同物。任何文档、注释、提示词提及 `open-ui` 时必须标明是哪一种：

| 形态 | 定义位置 | 读取/处理位置 | 状态 |
|---|---|---|---|
| `--open-ui` 进程启动参数 | `Zentwik.Core/Services/AutoStartService.cs:69` | `Zentwik.Worker/Program.cs:62` 读取，`:63` 在交给 Host 前从参数数组摘除 | 已实装（批次五） |
| `CommandOpenUi` 管道命令（值 `"open-ui"`） | `Zentwik.Core/Ipc/WorkerPipeContract.cs:108` | `PipeServerService.HandleAsync` 无分支，落 `default`（`:235`）返回「未知命令」 | **未实装** |

**理由**：混用会产生两类误判——① 照着文档发 `open-ui` 管道命令，收到「未知命令」；② 以为管道命令已实装，实际只是启动参数生效（带 `--open-ui` 启动时 UI 确实会起来，表现上很像「命令已生效」）。第二种更隐蔽，因为它有可观察的「成功现象」。

### 4.3 ShutdownIfOwned 竞态仍在（未修）

**规则**：`WorkerLauncher.ShutdownIfOwned()` 当前是 `public static void` + `_ = Task.Run(...)` 的 fire-and-forget 形态（`WorkerLauncher.cs:163`、`:171`），`App.xaml.cs:153` 同步调用且无 `.Wait()`。在它改为返回 `Task` 并由 `OnExit` 等待之前，**任何「UI 退出后 Worker 必已收到 shutdown」的判断都不成立**。

**理由**：`OnExit` 调用后立即 `Log.Flush()` / `Log.Dispose()`（`App.xaml.cs:158-159`）并进入进程退出，shutdown 命令的发送与进程退出并发。任务未完成时日志对象可能已被 Dispose，失败现场丢失；Worker 也可能根本没收到 shutdown 而继续常驻。另注意 `void` 方法没有 `.Wait()`——写成 `ShutdownIfOwned().Wait(...)` 编译不过，交接文档已记录这个误写。

### 4.4 git 命令的有限例外：仅允许 `git add` 指定文件

**规则**：Agent 被授权仅执行 `git add <任务提示词中明确列出的文件>`（如 `git add Zentwik.UI/Assets/Zentwik.ico`），**单次任务内只允许一条**。仍然禁止 `git add -A`、`git add .`、`git commit`、`git push`、`git status`、`git diff`、`git log` 及其他任何 git 命令。

**理由**：这是对「不执行 git 命令」红线的**有限例外，不是全面放宽**。起因是 4.1 的失败模式：Agent 按红线不能 `git add`，新增资源文件就永远进不了仓库，只能靠人工事后补救。放行单文件 `git add` 能闭合这条链；而 `git status` / `git diff` 属「查看」，放行它们会给 Agent 一个在核实环节跑 git 的理由，偏离「读文件取证」的既定做法。本例外自批次六文档同步任务起生效，后续批次沿用。
