## 第一部分：项目现状与工作原则

### 一、项目是什么

Zentwik 是一个 Windows 桌面调校工具，针对 AMD Ryzen 平台。核心功能：SMU 读写（Curve Optimizer、FMax）、基于 CPU Sets 的进程绑核、场景自动切换（检测到进程启动时切换调校方案）、进程优先级设置。

项目历史：ZenForge → Zenwik → Zentwik，经历 WPF → WinUI 3 → 回退 WPF 两轮 UI 迁移。**当前是双进程架构：`Zentwik.UI`（WPF 壳子，`asInvoker`）+ `Zentwik.Worker`（提权后台进程，`requireAdministrator`），通过命名管道通信。**

### 四、必须知道的十个技术事实

1. **`ProcessRefresher.Start()` 是唯一启动采样线程的入口**，Core 内部不调它。宿主不调则采样线程不存在，`SampleOnSamplerThread` 静默等 5 秒超时返回空，不抛异常不写日志。Worker 的 `BackendHostService` 必须调 `refresher.Start()`（`watcher.Start()` 之前）和 `refresher.Stop()`（`watcher.Stop()` 之后）
2. **`PipeOptions.CurrentUserOnly` 在跨完整性级别场景下不够**。提权 Worker + 非提权 UI，`CurrentUserOnly` 管道对中完整性客户端返回 `UnauthorizedAccessException`。必须用 `NamedPipeServerStreamAcl.Create` + 显式 `PipeSecurity`（当前用户 SID + `ReadWrite`）。`SetAccessControl` 在已创建的管道上会让 accept 循环 fault
3. **`System.IO.Pipes.AccessControl` 在 .NET 10 是共享框架内建程序集**，不需要 NuGet 包
4. **创建 `PipeRequest` / `PipeResponse` 必须显式赋值 `Version = WorkerPipeContract.ProtocolVersion`**。默认值 0 会被 `ValidateVersion` 拒绝，对端返回「版本不一致，请重新安装」——这个失败模式无法从日志归因
5. **`IHost` 接口没有 `Lifetime` 属性**（`Host` 类有）。用 `host.Services.GetRequiredService<IHostApplicationLifetime>()`
6. **UI 拉起提权进程必须 `UseShellExecute=true` + `Verb="runas"`**。`UseShellExecute=false` 抛 `Win32Exception 740`，不弹 UAC 也不启动进程。用户拒绝 UAC 时抛 `Win32Exception 1223`，不返回 null
7. **`LogOptions` 只给 `FilePrefix` 不设 `Directory`，日志落到 `%TEMP%`**。走 DI（`AddZentwikCore`）会自动填 `AppPaths().Logs`；手工 `new LogService` 必须显式设 `Directory`
8. **WPF + `UseWindowsForms` 并存时，`MessageBox` / `Application` / `Color` 等同名类型会 CS0104**，用 `using MessageBox = System.Windows.MessageBox;` 消歧义
9. **收托盘时销毁 `MainWindow` 而非 `Hide()`**，`ShutdownMode` 必须是 `OnExplicitShutdown`，托盘右键「退出」是彻底退出不等同于关闭窗口
10. **`UiSettings.BackendService` 字段**：Worker 绝不读（双进程下常驻与否由拉起方决定），UI 可读但仅作展示

### 第一件事：不要急着写功能，先跑实机验证

批次五声称交付了一份「实机验证清单」（五步：安装、首次启动、开机自启、关闭行为、日志位置），但**仓库内未落盘**；本次重建，见 `docs/实机验证清单.md`。**这份清单从来没有在干净环境跑过。** 发布链断点见事实卡 §1.3——本次 G 项只处理 ico 的 `git add`；`dist/portable/` 填充与 ISCC 环节因核实结果与提示词预期不符，已停下待裁决。

开发机上有 PawnIO、有 .NET 10、有装过的旧配置。干净 Windows 环境什么都没有。这两者的差异，就是「开发验收通过」和「用户装不上」的差距。

**具体做什么：**

1. 找一台干净 Windows 10/11 机器（虚拟机也行，但不要快照回滚后再用，否则驱动残留会骗你）
2. 按批次五第六件的五步清单跑一遍
3. **重点看三件事**：
   - 安装包能不能装（`Zentwik.iss` 没有 .NET 10 Runtime 检测，用户没装 runtime 会直接启动失败，但安装过程不会有任何提示）
   - 没装 PawnIO 时 Worker 能不能启动（SMU 探测失败不阻断，但用户会看到什么？）
   - 开机自启能不能触发（`schtasks` 在组策略收紧的机器上可能静默失败）

**这一步大概率会暴露问题。** `Zentwik.iss` 缺 .NET 检测是 TODO 里记录过的，但那只是「已知」，不是「已修」。你需要在实机验证时确认这个问题的严重程度——是「用户点安装后程序跑不起来」还是「安装时就提示缺 runtime」，两者的产品体验差距很大。

**不要跳过这一步直接做 UI。** 如果发布链有洞，做完 UI 再回头修，等于把「装不上」的问题延后到功能完整之后才暴露，返工成本是现在的几倍。

### 第二件事：功能开发的排序逻辑

跑完实机验证后，按这个顺序做：

#### 第 1 优先：调校页 + `apply-tuning` IPC

**为什么最先做这个：**
- 调校（CO/FMax）是产品定位的第一句话，最核心
- 它是「UI ↔ Worker」完整链路的第一次验证——UI 读 `tuning.json`、用户改值、IPC 发给 Worker、Worker 写 SMU、回读校验、UI 显示结果
- 这条链路跑通了，进程页、配置页的模式就清楚了

**注意：** `apply-tuning` 的服务端逻辑需要注入 `TuningApplyService`，它已经在 `AddZentwikCore` 里注册了。如果 `PipeServerService` 的构造函数没有这个依赖，加进去——这是功能范围的合理改动，不是架构改动。

#### 第 2 优先：进程页 + 进程列表查询 IPC（新增）+ `unbind-all`

**为什么排第二：**
- 进程绑核是 README 第二句，核心功能
- 需要 `snapshot-logs` 的变体或者新增查询命令（`ProcessRefresher` 有 `Latest` 属性，但要通过 IPC 拿给 UI 需要新命令，`snapshot-logs` 是给日志用的，不要混用）
- `unbind-all` 是进程页的**附带**操作（解除绑核），进程页的**核心 IPC 依赖**是「查询进程列表的新命令」+ 展示绑核状态；不要因为标题里有 `unbind-all` 就以为它是主依赖
- **这里可能会发现 IPC 命令不够用**——如果 `snapshot-logs` 不能复用来传进程列表，需要新增命令。新增命令属于功能范围还是架构范围？我的判断：**新增命令是功能范围**，因为 `WorkerPipeContract` 是设计成可扩展的，加一个 `CommandSnapshotProcesses` 和现有的 8 个命令并列，不改变协议结构

#### 第 3 优先：配置页 + `ui.json` 完整读写

**为什么排第三：**
- `ui.json` 有 13 个字段，批次五只接了 `AutoStart` 一个
- 配置页是「用户能自己调」的基础，没有它，用户只能手改 JSON
- 它不依赖新的 IPC 命令（读写都在 UI 侧通过 `UiSettingsStore`），所以技术上最简单

#### 第 4 优先：场景规则编辑器 + `snapshot-logs`

**为什么排第四而不是更早：**
- 场景自动切换是核心卖点，但当前是「框架实装、用户用不了」的状态——规则只能手编 `scenarios.json`
- 但它的依赖链最长：需要 `snapshot-logs` 实装（用于显示规则命中日志）、需要进程列表（判断规则里的进程名）、需要方案列表（规则指向哪个方案）
- **先把前面三个做完，场景规则编辑器才有东西可指**

**注意：** `ScenarioService` 的规则模型可能不够用。事实卡 §2.1 记录它支持 ProcessRunning / OnBattery / OnAcPower 三类触发，但 UI 编辑器可能需要「进程路径匹配」「窗口标题匹配」之类。如果发现模型不够，**先报告，不要自行改 Core**——改规则模型会影响 `scenarios.json` 的 schema，涉及用户数据迁移。

#### 第 5 优先：日志页

**为什么排最后：**
- 日志不影响核心体验，用户不用它也能调校
- 它是排查问题的工具，等前面功能都跑通了，日志页才有意义
- `snapshot-logs` 实装时要注意日志数据量——`LogService` 内存队列上限 200 条，但每条的 `Message` 可能很长，管道传输时要注意 64KB 上限

#### 第 6 优先：UFIX 第 13/14 条修复

这两个是批次五发现的产品缺陷，但不阻塞主流程：
- 第 13 条（任务计划与 `ui.json` 不一致）触发条件是「`Save()` 抛异常」，概率低
- 第 14 条（UI 超时 10 秒 vs Worker 30 秒）触发条件是「`schtasks` 极慢」，概率低

**等功能页都做完了再修**，因为修这两个需要改 `OnAutoStartChanged` 的回滚逻辑，如果 UI 还没定型，改了可能白改。

#### 第 7 优先：§7.4 第 3/4 条、功耗墙裁决

- §7.4 第 3 条（关闭前存完整窗口状态）：涉及 `ui.json` 加字段，属于产品体验优化
- §7.4 第 4 条（托盘确认文案）：小改动，随时可做
- 功耗墙：**先做产品决策**——是删 README 的承诺，还是重写实现。这个决策不做，做别的都是绕路

### 第三件事：每做一个功能，问三个问题

1. **这个功能在「没装 PawnIO」的机器上会怎样？**（降级路径）
2. **这个功能失败了，用户怎么知道？**（错误反馈）
3. **这个功能如果被误操作，用户怎么恢复？**（撤销/回滚）

第 1 个问题的答案在事实卡 §1.5：SMU 读写失败时 `IsAvailable=false`，所有读写短路。但 UI 要显示什么？「SMU 不可用」还是「请安装 PawnIO」还是「仅绑核功能可用」？——这个文案要设计。

第 2 个问题：`apply-tuning` 失败时 `PipeResponse.Success=false` + `Message`，UI 要显示 `Message` 原文还是自己编文案？我的建议：**显示 `Message` 原文**，因为 Worker 侧的失败原因更准确（比如「第 3 核写入被拒」），UI 编的文案会丢失细节。

第 3 个问题：调校页的 CO 值改了但没应用，用户关窗口，值丢了——要不要提示「未保存」？`apply-tuning` 成功了但硬件不稳定，用户想撤销，有没有「恢复出厂」按钮？

### 第四件事：不该做的五件事

1. **不要重新设计架构。** 双进程、命名管道、显式 DACL 已经跑通，改了就是重新踩一遍坑
2. **不要在功能不完整前追求 UI 美化。** 开发指南里「现有 UI 设计不强求」是对的，第一版功能页应该朴素——能操作就行
3. **不要按「页面」孤立地做。** 做完调校页就做进程页、做完进程页就做配置页，会做出四个孤岛。**按「用户场景」串起来做**——用户想「给游戏降压并绑核」，这条链路需要调校页 + 进程页 + 场景规则
4. **不要忽略 UFIX 和 TODO 的记录。** 那里面每一条都是踩过的坑。比如 UFIX 第 12 条「`LogOptions` 不设 `Directory` 落 `%TEMP%`」，如果做日志页时新建一个 `LogService` 读历史日志，忘记设 `Directory`，又会踩一遍
5. **不要让审核员代替实测。** 批次五的三处偏离（`-silent` 不崩、`IHost.Lifetime` 不存在、`schtasks` 被拦截）都是 Agent 实测发现的，审核员没预判到。**提示词里必须留「发现与提示词不符时停下来报告」的空间**，不要写得太死

### 第五件事：可能踩的坑

**坑 1：实机验证会暴露 `Zentwik.iss` 的更多问题。** 除了 .NET 10 检测缺失，还有可能：`Source: "..\..\dist\portable\*"` 里的 `dist/portable` 在用户机器上不存在（`zip_portable.py` 是读 `dist/portable` 写 zip，不生成该目录；安装包本地出时需手工填充 `dist/portable`。）；图标路径 `SetupIconFile=..\..\Zentwik.UI\Assets\Zentwik.ico`（`Zentwik.iss` 的 `SetupIconFile`）是**相对于 `build/installer/` 的源码树路径**，ISCC 编译时读源码树，不涉及 `publish/` 输出（「`publish` 扁平结构导致失效」这个理由不成立）。**已确认的断点（非假设）**：`Zentwik.UI/Assets/Zentwik.ico` 在本地磁盘存在（批次五第六件从 `Legacy/` 复制，32571 字节），但 `git ls-files` 显示未被跟踪，CI checkout 后该文件不存在，ISCC 编译 `SetupIconFile` 指向的路径会直接失败，**发布链当前断在此处**（已核实 `.gitignore` 第 34–40 行仅忽略 png/jpg 等、且 `!Assets/**` 放行 `Assets/` 下一切，无排除规则；原因是批次五 Agent 按红线未 `git add`）。**修复：`git add Zentwik.UI/Assets/Zentwik.ico` 并提交——这是发布链当前第一优先级修复项，排在实机验证之前。**（详见 `docs/UFIX.md` 第 15 条、事实卡 §1.3）

**坑 2：调校页做完发现 SMU 写入在某些 Ryzen 型号上失败。** 这不是代码问题，是硬件差异（`ZenStates-Core` 对某些型号的支持不完整）。但 UI 要能优雅报错——显示「此型号不支持 FMax 写入」而不是「写入失败」这种含糊提示。`SmuReader` 的 `LastError` 会给出具体原因，UI 要透传。

**坑 3：场景规则编辑器做到一半发现规则模型不够用。** 如果用户想要「Chrome 打开超过 10 个标签时切方案」这种规则，当前模型表达不了。**先做当前模型能表达的部分**（进程运行、电池/交流电），扩展留到后面。事实卡 §3.4 第 8 条已记录「切换失败回滚」和「重扫解绑语义」未实装，那些是规则执行层面的问题，不是规则编辑层面的问题，先分开。

**坑 4：`snapshot-logs` 实装时发现日志量太大。** `LogService.Snapshot()` 返回 `IReadOnlyList<LogEntry>`，200 条，每条可能 2000 字符，序列化后可能超过 64KB。需要分页——但分页需要新增 IPC 命令参数（`PipeRequest.Payload` 可以传分页参数），这不改协议结构，属于功能范围。

**坑 5：开机自启在干净环境可能不工作。** 任务计划用 `InteractiveToken` + `HighestAvailable`。**「UAC 被禁用」本身不会让管理员账户降级**：在「以管理员批准模式运行所有管理员」被禁用的机器上，若当前用户是管理员组成员，`HighestAvailable` 仍拿到完整管理员令牌。真正会失败的场景是：① 当前用户**不是管理员组成员**，`HighestAvailable` 拿到标准用户权限，Worker 启动后 SMU 写入失败；② 组策略收紧任务计划权限，导致 `schtasks /Create` 静默失败。实机验证时确认：用管理员账户跑一遍、用标准用户账户跑一遍、检查目标机器组策略是否限制任务计划创建。

### 第六件事：流程建议

批次一到批次五的流程是有效的：**架构师出提示词 → 审核员挑刺 → Agent 执行 → 用户验收**。

这个流程保持，但有一点调整：**审核员的职责是「挑提示词的刺」，不是「预判 Agent 会遇到什么」**。批次五审核员写「`-silent` 可能让 Worker 崩」，结果 Agent 实测发现不崩——审核员基于假设提了建议，Agent 用实测推翻了。这不是审核员失职，是分工的必然：审核员看的是提示词，Agent 看的是代码。

所以新架构师写提示词时：
- **技术细节要确定**（查过代码、查过文档），不确定的写「报告实际现象」
- **给 Agent 留「发现与提示词不符时停下来报告」的空间**
- **验收标准写「实际观察结果」而不是「预期结果」**——比如「验证 `-silent` 是否会崩，记录现象」，而不是「`-silent` 会让 Worker 崩，确认已删」

### 最后

批次一到批次五，把架构从「多次搬迁后实现错误」的状态做到了「双进程跑通、文档齐全、核心链路有测试」。这个状态是可持续的。

后面是功能，不是架构。功能比架构慢、比架构琐碎、比架构容易做出「看起来能用实际不能用」的东西。**每做完一个功能，在干净环境里跑一遍，比看代码审查有用。**

慢一点、查一下、别凭记忆。这三件事比聪明重要。

祝顺利。
