| # | 断点 | 归属 | 性质 |
|---|---|---|---|
| ① | `ico` 未被 git 跟踪 | **便携 zip 链** | **当前断点**，非设计状态；`git add` + commit/push 后修复 |

**结论（三段，勿混时态）**：

1. **当前（ico 未 commit/push 前）**：`ico` 未被 git 跟踪，CI 干净 checkout 后 `dotnet publish Zentwik.UI` 失败，**便携 zip 链当前断**。
2. **commit/push 后**：`ico` 进入仓库，CI 可产出便携 zip（`publish/*` → `Zentwik-win-x64.zip`）。

### 1.5 硬件依赖边界【事实】

| 能力 | 依赖 | 失败表现 |

### 2.1.1 采样线程的启动职责（批次三收尾补入）

`ProcessRefresher` 不会自己启动。**`Start()`（`ProcessRefresher.cs:352`）是全仓唯一启动采样线程 `Zentwik.ProcessSampler` 的入口**，Core 内部没有任何地方调用它——旧架构里这一句写在宿主 `Legacy/WPF/Zentwik/App.xaml.cs:172` 与 `:263`。

双进程下 **Worker 是唯一宿主，必须由 `BackendHostService` 负责启动与停止**：`StartAsync` 里 `_refresher.Start()` 要排在 `_watcher.Start()` **之前**，`StopAsync` 里 `_refresher.Stop()` 排在 `_watcher.Stop()` **之后**（先停消费者再停生产者）。

**不调的后果是静默的**：采样线程不存在时，`SampleOnSamplerThread(timeout)`（`ProcessRefresher.cs:581-594`）只是把 waiter 入队、`RequestSample()` 往信号量 Release 一次，然后**等满超时**（`ProcessWatcher` 与 `ScenarioMonitor` 都用 5 秒）返回 `Latest`（空列表）。**不抛异常、不写日志**。表现为：

- `ProcessWatcher.Start()` 的启动补扫拿到空快照 → 启动前已在运行的进程不会被绑核；
- `ScenarioMonitor.Evaluate()`（`:223`）每次评估空转 5 秒 → 进程类场景规则永远命中不了。

`ProcessRefresher.Stop()`（`:503-527`）**没有 `Join`**：只 `Cancel` + 补一次信号 + `Dispose`，不会阻塞宿主的 `StopAsync`。

### 4.4 第四条：WMI 走事件，不是轮询

**代码证实（事件模式）**。`ProcessWatcher.cs:210-216` 两条 WQL 常量：

```
SELECT * FROM __InstanceCreationEvent WITHIN 2 WHERE TargetInstance ISA 'Win32_Process'
SELECT * FROM __InstanceDeletionEvent WITHIN 2 WHERE TargetInstance ISA 'Win32_Process'
```

订阅点 `:228` / `:231`（`new ManagementEventWatcher(new WqlEventQuery(...))`），字段声明 `:55-56`。`:203-207` 的注释正是当年那个语法坑的记录：「事件查询的 SELECT 列表里不能出现 `TargetInstance.Xxx` 这种带点号的属性路径 —— 那是普通实例查询的语法，用在 `__Instance*Event` 上 `WqlEventQuery` 会直接抛『无效的参数』」。`WITHIN 2` 的理由写在 `:208`（WMI 服务内部轮询粒度，越小越耗 CPU）。

**轮询只在 WMI 不可用时降级**：`FallbackIntervalMs = 3000`（`:83`），触发日志 `:157`（有界面弹提示）/ `:185`（无界面只记 Warn）。结论：**不是无意识在跑轮询，是事件优先 + 显式降级**。

- `_hostVisible` 默认 `true`，Worker 无窗口也**不会**因它停摆 —— 这一道闸门本身不致命。
- 真正会停住的是**同一条 `if` 里的另一半** `IsWatched`（`ProcessRefresher.cs:229-232`，`_watcherCount > 0`）。Worker 里没有 UI，没有人调 `AcquireWatch()`（`:238`），`IsWatched` 恒为 `false`，采样线程一直停在 `WaitAny`（`:410-422`）。
- 但它不是「永不启动」：`RequestSample()` 走 `_sampleNowSignal`（`:386` 置位），`WaitAny` 的 `index == 1` 分支会消费掉请求并采一帧（`:424-432`）。所以准确说法是：**Worker 里不会按 `IntervalSeconds` 周期采样，只能被显式请求唤醒采一帧。**
- 结论：双进程落地时，若 Worker 需要周期采样（进程列表快照、绑核重扫），必须在 Worker 侧自行 `AcquireWatch()` 或改用 `RequestSample` 定时驱动，**不能依赖 UI 调 `SetHostVisible(true)` 把闸门打开**。

### 5.1 两个进程的权限基线

| 进程 | 清单 `requestedExecutionLevel` | 弹 UAC 的时机 |
|---|---|---|
| `Zentwik.UI` | `asInvoker`（**不** `requireAdministrator`） | 只有在它自己去拉起 Worker 时弹一次（见 5.3） |
| `Zentwik.Worker` | `requireAdministrator` | 手动双击 Worker 时弹；由任务计划或已提权进程拉起时不弹 |

### 5.2 四个启动场景

| 场景 | 启动方 | 是否弹 UAC | 依据 |
|---|---|---|---|
| 开机自启 | 计划任务（`HighestAvailable` + `InteractiveToken`） | **不弹** | 与 1.4 现行自启写法一致；`HighestAvailable` 在 UAC 开启时拿到的是提权令牌，不经 `consent.exe` |
| Worker 拉起 UI | Worker（已提权） | **不弹** | 子进程继承父进程的提权令牌 |
| 用户手动双击 UI，Worker 已在跑 | UI 连命名管道 | **不弹** | UI 自身 `asInvoker`，连管道不需要提权 |
| 用户手动双击 UI，Worker 不在 | UI `Process.Start` 拉 Worker | **弹一次** | 跨完整性级别启动，必须走 `consent.exe`。**批次四收尾补入**：UI 用 `Process.Start` + `UseShellExecute=true` + `Verb="runas"` 拉起 Worker。`UseShellExecute=false` 会抛 `Win32Exception 740`（`ERROR_ELEVATION_REQUIRED`），不弹 UAC 也不启动进程——批次四实测发现 |

> **【批次三收尾补入】上表第 3 行的前提**：「UI 连命名管道不弹 UAC」成立的前提是 **Worker 用显式 `PipeSecurity` 给当前用户 SID 授予 `ReadWrite`**。若改用 `PipeOptions.CurrentUserOnly`，在跨完整性级别场景下（提权 Worker ← 非提权 UI）非提权客户端连不上，实测抛 `UnauthorizedAccessException`（`Access to the path is denied.`）。实现细节见 §6.5。

### 6.5 服务端管道安全（批次三收尾补入）

**最终实现**（`Zentwik.Worker/PipeServerService.cs`）：

以下为 `PipeServerService` 的私有静态方法 `CreatePipeSecurity()`，在 `AcceptLoopAsync` 中作为 `NamedPipeServerStreamAcl.Create` 的 `pipeSecurity` 参数传入。

```csharp
using NamedPipeServerStream server = NamedPipeServerStreamAcl.Create(
    WorkerPipeContract.PipeName,          // "Zentwik.Worker"
    PipeDirection.InOut,
    maxNumberOfServerInstances: 1,
    PipeTransmissionMode.Byte,
    PipeOptions.Asynchronous,
    inBufferSize: 0,
    outBufferSize: 0,
    pipeSecurity: CreatePipeSecurity(),   // 当前用户 SID + ReadWrite，不设 SACL
    inheritability: HandleInheritability.None,
    additionalAccessRights: default);

private static PipeSecurity CreatePipeSecurity()
{
    PipeSecurity security = new();
    security.AddAccessRule(new PipeAccessRule(
        WindowsIdentity.GetCurrent().User!,
        PipeAccessRights.ReadWrite,
        AccessControlType.Allow));
    return security;
}
```

**定案**：显式 `PipeSecurity` + 当前用户 SID（`WindowsIdentity.GetCurrent().User`）+ `PipeAccessRights.ReadWrite`。**不用 `PipeOptions.CurrentUserOnly`，不用 `BuiltinUsers` 组。**

| 选择 | 结论 | 依据 |
|---|---|---|
| `PipeOptions.CurrentUserOnly` | **不用** | 提权 Worker 创建的管道对中完整性（非提权）客户端一律 `UnauthorizedAccessException`，而 UI 正是这个形态 |
| `BuiltinUsers` + `ReadWrite` | **不用** | 那是「所有本地用户」组，多用户机器上等于允许其他登录用户向提权 Worker 发 `shutdown`，与 `CurrentUserOnly` 的初衷相反 |
| 当前用户 SID + `ReadWrite` | **采用** | 实测非提权客户端可连接；语义与 `CurrentUserOnly` 相同（只有同一个 Windows 用户能连），且没有那层导致跨完整性级别拒绝的附加限制 |

实测对照（客户端 `MOTUIC-LAPTOP\ZMotu`，完整性级别 Medium / `S-1-16-8192`）：

| DACL | 非提权客户端 |
|---|---|
| `CurrentUserOnly` | ❌ `UnauthorizedAccessException` / `Access to the path is denied.` |
| 当前用户 SID `Read` | ❌ 同上（客户端要读写，只给读自然被拒） |
| 当前用户 SID `ReadWrite` | ✅ 连接成功，收到 `{"Version":1,"Success":true,"Message":"pong","Payload":null}` |
| 当前用户 SID `ReadWrite \| Synchronize` | ✅ |
| 当前用户 SID `FullControl` | ✅ |
| `BuiltinUsers` `ReadWrite` | ✅（但不采用） |

> 上表只覆盖 `ping`。同一批实测中，**非提权客户端发 `shutdown` 也通过**：收到 `{"Version":1,"Success":true,"Message":"bye","Payload":null}`，进程在 0.21 秒内退出、无残留。（**批次三收尾补入**）

**三条技术事实**（均为批次三实测，不是推测）：

| # | 事实 | 影响 |
|---|---|---|
| 1 | `System.IO.Pipes.AccessControl` 在 .NET 10 **是共享框架内建程序集**（`Microsoft.NETCore.App.Ref/10.0.14/ref/net10.0/System.IO.Pipes.AccessControl.dll`），**不需要额外 NuGet 包** | `PipeSecurity` / `PipeAccessRule` / `NamedPipeServerStreamAcl` 直接可用；先编译，报「找不到类型」再考虑加包 |
| 2 | **`SetAccessControl`（`PipesAclExtensions` 扩展方法）在已创建的管道上会抛异常**（句柄没有 `WRITE_DAC`）。该调用若写在 `try` 之外，异常会让整个 accept 循环 fault、管道直接消失（现象是「管道根本不存在」，不是「连接被拒」） | 必须在**创建时**用 `NamedPipeServerStreamAcl.Create` 带上安全描述符，不能「先建后改」 |
| 3 | `NamedPipeServerStreamAcl.Create` 的参数名是 **`inheritability`**，不是 `handleInheritability`（写错是 `error CS1739`） | 签名：`(pipeName, direction, maxNumberOfServerInstances, transmissionMode, options, inBufferSize, outBufferSize, pipeSecurity, inheritability, additionalAccessRights)` |

**未解决的部分**：以上只解决「同一用户、跨完整性级别」。**跨用户**（A 用户起的 Worker、B 用户的 UI）仍然不可用，根因是 `Global\` 互斥体而非管道 DACL，见 `docs/UFIX.md` 第 10 条。

### 7.2 托盘归属（写死，不留选项）

**托盘图标在 UI 进程里创建，用 WinForms `NotifyIcon`。** `Zentwik.UI.csproj` 加 `<UseWindowsForms>true</UseWindowsForms>`，与 WPF 共存于同一 csproj。**Worker 不持有任何托盘，也不引用任何 UI 库。**

理由：Worker 是提权进程，托盘交互（右键菜单、点击唤起窗口）需要接收用户输入消息，而 UIPI 隔离会让高完整性进程的窗口接收不到低完整性进程的输入消息，导致托盘菜单点击失效；UI 进程非提权，托盘稳定可用。

因此：
- **「收托盘」** = 销毁 `MainWindow`，但 **UI 进程本身存活**，托盘图标由 UI 进程持有（图标不闪、不重建）。
- **「只留 Worker」** = UI 进程彻底 `Environment.Exit(0)`，**托盘图标随 UI 进程退出而自动消失**（Windows 会清理 shell 通知区），Worker 常驻。
- 两者语义完全不同：前者还有 UI 进程能接托盘点击；后者连进程都没有，用户下次只能重新启动 UI。

### 7.4 「收托盘」的实现约束

- **销毁 `MainWindow`，不是 `Hide()`**。`Hide()` 会保留整棵可视树与设备资源，内存停在 50-70MB；销毁窗口、只留 `Application` 对象与 `NotifyIcon`，内存预期 30-40MB。
- 保留 WPF `Application` 对象（否则托盘消息循环没了）与 `NotifyIcon` 实例；`ShutdownMode` 必须是 `OnExplicitShutdown`，否则销毁主窗口会直接结束应用。
- 托盘图标用 WinForms `NotifyIcon`，`<UseWindowsForms>true</UseWindowsForms>` 与 WPF 同 csproj 共存；**不用第三方托盘库**（多一个依赖，且 AOT / 裁剪下行为不可控）。
- `MainWindow` 销毁前保存 `ui.json`（窗口尺寸、位置、当前页），下次打开从配置读回恢复状态，不靠「记住上次 Hide 时的内存状态」。
- 托盘右键菜单的「退出」是**彻底退出**（等价 B1），不等同于关闭窗口（B2）。两者必须给不同的菜单项与不同的确认文案。
